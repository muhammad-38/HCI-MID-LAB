Section 1

Overview

The PolyLine Editor allows a user to create and edit drawings made up of connected line segments (polylines) using a mouse and keyboard on a browser canvas. Phase 3 takes the requirements and analysis from the previous phases and turns them into a precise, implementable design — covering the interface layout, interaction modes, data structures, algorithms, and the HCI principles that justify each decision.

i
This design specification is the contract between analysis and implementation. Phase 4 (Implement & Deploy) must be buildable from this document alone — no guesswork required.

Design goals

Goal 1 Direct manipulation

Every action must produce immediate, visible feedback on the canvas. No dialog boxes for routine operations.

Goal 2 Keyboard parity

Every function accessible from the toolbar must also be reachable via a single keypress matching the textbook spec.

Goal 3 Zero install

The entire application ships as a single HTML file. Open in browser, use immediately. No build step, no server.

Goal 4 Persistence

Drawings must survive a page reload via JSON save/load. The file format must be human-readable and versioned.

Data Structure Design

Polyline object schema

// Single polyline object
{
  id:       Number,        // auto-increment, never reused
  name:     String,        // "Line 1", "Line 2", ...
  color:    String,        // CSS hex, from 12-color palette
  points:   Array<{x:Number, y:Number}>,  // ordered vertices
  finished: Boolean       // false = drawing in progress
}

// Global state
const polys    = [];    // Array<Polyline>, max 100
let   activeIdx = -1;  // index of polyline being drawn (-1 = none)
let   mode     = 'draw'; // 'draw'|'move'|'delete'|'insert'

JSON persistence format

// polylines.json — save file format
{
  "version": 1,
  "polys": [
    {
      "id": 1,
      "name": "Line 1",
      "color": "#4f8ef7",
      "points": [
        { "x": 120, "y": 80 },
        { "x": 240, "y": 160 }
      ],
      "finished": true
    }
  ]
}
✓
The version field is included so future implementations can detect and migrate older save files. Always increment on breaking schema changes.

Color palette (12 colors, cycles on new polyline)

All colors are high-contrast against the dark canvas background (WCAG AA for large text).

Section 5

Algorithm Specifications

A — Find nearest vertex

Used by Move and Delete modes to identify which point the user intends to interact with.

Iterate over every point in every polyline. Compute Euclidean distance: d = √((mx−px)² + (my−py)²)

Track the minimum d and corresponding {polyIdx, ptIdx} pair.

Return result only if d ≤ 20px (hit threshold). Otherwise return no-hit.

function findNearest(mx, my) {
  let best = { polyIdx: -1, ptIdx: -1, d: Infinity };
  for (poly of polys)
    for (pt of poly.points) {
      const d = Math.hypot(mx - pt.x, my - pt.y);
      if (d < best.d) best = { ...indices, d };
    }
  return best;
}

B — Delete vertex

Call findNearest(mx, my). If no hit, do nothing.

If the polyline has exactly 1 point, remove the entire polyline from polys[].

Otherwise: poly.points.splice(ptIdx, 1). The renderer automatically draws a segment between the now-adjacent neighbours — no explicit reconnect needed.

C — Insert point on segment

Projects the mouse position onto the nearest segment and inserts a new vertex at that projection.

For each consecutive pair (A, B) in each polyline, compute vector AB and its squared length |AB|².

Project mouse M onto segment: t = clamp( dot(M−A, B−A) / |AB|² , 0, 1 )

Projection point: P = A + t·(B−A). Distance to cursor: d = |MP|.

Track minimum d across all segments. If d ≤ 15px, insert P at points.splice(afterIdx + 1, 0, P).

function projectOntoSegment(M, A, B) {
  const dx = B.x-A.x, dy = B.y-A.y;
  const lenSq = dx*dx + dy*dy;
  if (lenSq === 0) return A;
  const t = Math.max(0, Math.min(1,
    ((M.x-A.x)*dx + (M.y-A.y)*dy) / lenSq
  ));
  return { x: A.x + t*dx, y: A.y + t*dy };
}

D — Snap to grid

Applied at event capture time — every incoming mouse coordinate passes through this before being stored.

const GRID = 10; // px
function snap(v) {
  return snapEnabled ? Math.round(v / GRID) * GRID : v;
}
Section 6

HCI Principles Mapping

Each design decision maps to at least one of Nielsen's 10 usability heuristics. This table is the justification for every choice made in Sections 2–5.

H1

Visibility of system status

Status bar updates on every action. Mode badge in header reflects current state. Preview line shows the next segment before the user commits. Hover ring shows which vertex will be affected before the click happens.

H2

Match between system and real world

Vertices appear exactly where clicked. Snap-to-grid aligns with mental model of a drawing grid. Dimensions in the status bar use pixel units — the same coordinate system shown on screen.

H3

User control and freedom

Esc always resets to draw mode. Finish (F) locks a polyline without deleting it. Sidebar delete button removes individual polylines. Clear all requires confirmation. Every destructive action is recoverable except clear-all.

H4

Consistency and standards

Keyboard shortcuts match the textbook specification exactly (B, D, M, R, Q). Toolbar labels include the key shortcut so both interaction styles are visible at the same time.

H6

Recognition over recall

All modes and actions are visible in the toolbar — the user never has to remember a command. The help overlay (press ?) lists every shortcut. The status bar provides a contextual hint for the current mode.

H7

Flexibility and efficiency of use

Expert users operate entirely via keyboard shortcuts. Beginners use toolbar buttons. Both paths produce identical results. Grid snap is opt-in for precision work without slowing casual use.

★
Fitts's Law application: The 20px hit radius for vertex selection is a direct application of Fitts's Law. Small vertex circles (r=4) would require pixel-perfect clicking. The 20px hover zone makes the effective target area 5× larger, dramatically reducing pointing time and error rate.

Section 8

Challenges & Confusions

The following were the genuine design-phase difficulties encountered — listed as the teacher encouraged.

1

Mode vs. tool mental model

Should "Delete" and "Move" be modes (persistent until switched) or tools (active only while held)? Decided on persistent modes to match the textbook spec, but tool-style holding (like Photoshop's Alt key) would feel more fluid for experienced users.

2

Hit threshold calibration

20px for vertices and 15px for segments were chosen empirically. Too small causes missed clicks; too large causes ambiguity when vertices are close together. A proper solution would use a spatial index (e.g. quadtree) and dynamic threshold based on zoom level.

3

No undo in spec

The original specification does not include undo. This is a significant usability gap — delete is irreversible. An undo stack was proposed as an extension but not in the base spec. Decided to follow the spec strictly and flag this as a known limitation.

4

Coordinate system on resize

HTML Canvas pixel dimensions are separate from CSS layout dimensions. Without explicit sync, a resized window stretches all existing drawings. Resolved by using ResizeObserver to reset canvas.width/height on container resize, at the cost of clearing the canvas — hence the need for the JSON save/load system.
